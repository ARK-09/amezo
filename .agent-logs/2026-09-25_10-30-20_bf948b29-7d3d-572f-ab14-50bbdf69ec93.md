## Hooks: they were dead everywhere except your Windows machine

`.claude/settings.json` ran the hook as `command: "py"`. `py` is the Windows Python launcher; it doesn't exist on Linux or macOS. So in this cloud session (Linux) the hook process failed to spawn with exit 127 before a single line of `capture.py` ran — your prompt for this task wasn't captured. Every log in `.agent-logs/` was written from Windows (the transcripts still carry `C:\Users\...` paths). The script's "always exit 0" safety net can't help when the interpreter itself is missing.

What was *not* wrong, checked against the current hooks reference: the config shape (`command` + `args` is the documented exec form; `timeout` and `statusMessage` are real fields), and `Stop` really does supply `last_assistant_message`, so the transcript scan is a genuine fallback.

The fix is `python3 … || py -3 …` under `shell: "bash"` — `capture.py` always exits 0, so the fallback only fires when the first interpreter can't be launched at all, and since nothing read stdin in that case the payload arrives intact (verified). **Proof it works: the fixed hook wrote `.agent-logs/2026-09-25_10-30-20_bf948b29….md` in this very session.**
