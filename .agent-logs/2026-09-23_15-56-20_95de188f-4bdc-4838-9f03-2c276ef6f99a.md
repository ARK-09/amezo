Two separate mechanisms, not one — details below, plus where I'd push back.

## Foundation (both features hang off this — not fully spec'd, just enough for FKs)

```
product(id, brand_id, title, gtin)
seller(id, name)
brand(id, name)
offer(id, product_id, seller_id, price, condition, warranty_terms_id nullable)
order(id, buyer_id, placed_at)
order_line(id, order_id, offer_id, product_id, seller_id, unit_price, quantity)
```

`order_line` already snapshots `offer_id/product_id/seller_id/unit_price` at purchase — that snapshot habit is what both features extend.

## Feature 1 — warranty on the offer

```
warranty_terms(id, warrantor_type: brand|seller, warrantor_id, product_id,
                duration_months, coverage_text, doc_url, version,
                effective_from, effective_to)

brand_authorization(id, brand_id, seller_id, product_id, verified_at,
                     expires_at, revoked_at)
-- gates whether a seller may point offer.warranty_terms_id at a brand's terms

order_line_warranty(id, order_line_id, warranty_terms_id,
                     warrantor_type, warrantor_id, warrantor_name_snapshot,
                     coverage_text_snapshot, duration_months_snapshot,
                     starts_at, ends_at)
-- frozen copy, taken once at purchase

warranty_claim(id, order_line_warranty_id, opened_at, issue_description,
               status, decision_type: repair|replace|refund|deny|withdrawn,
               decided_at, fulfilled_at)
```

Relationships: `order_line 1—0..1 order_line_warranty`, `order_line_warranty many—1 warranty_terms`, `offer many—1 warranty_terms`, `warranty_claim many—1 order_line_warranty`.

## Feature 2 — refund custody and settlement

```
return_request(id, order_line_id, reason, requested_at, status)

return_custody_event(id, return_request_id,
                      type: label_created|dropped_off|carrier_scan|
                            received_at_facility|graded_match|graded_mismatch,
                      occurred_at, location, actor)

refund(id, source_type: return|warranty_claim, source_id, order_line_id,
       amount, status: pending|issued|settled|failed|reversed,
       processor_ref, issued_at, settled_at)

refund_reversal(id, refund_id, reason_code, evidence_id,
                 notice_sent_at, charge_scheduled_at, outcome)
```

Note `refund.source_type/source_id` — decided below, see conflict 2.

## Is it one mechanism or two

Not one. Two, and forcing them into a single polymorphic table would cost more than it saves.

**Mechanism A — frozen-at-purchase.** A pre-purchase promise (warranty terms) copied immutably onto the order line the moment of sale, so a later dispute reads the copy, never the live row. Only warranty uses this today. Refund doesn't — its amount comes from what was already paid, not from a separate promise shown before purchase.

**Mechanism B — decision ≠ fulfillment.** A claimed/decided state is never the same row/flag as the confirmed/delivered state; the gap between them is where disputes and reversals live, and reversal requires evidence + notice, not just a flag flip. Both features need this: `warranty_claim.decided_at` vs `fulfilled_at`, `refund.issued_at` vs `settled_at`.

So: one shared *principle* (B), expressed as two separate state machines, plus mechanism A that only warranty currently uses. Don't build a generic "promise" or "claim" table across both — the domains (repair/replace vs. money) diverge too fast for a shared table to pay for itself. `ponytail: two similar shapes stay two tables until a third shows up.`

One place I *would* unify: evidence attachment (`return_custody_event`, `warranty_claim`, `refund_reversal` each want photos/docs). That's identical shape everywhere — file + who + when — so:

```
evidence(id, attached_to_type: return_custody_event|warranty_claim|refund_reversal,
         attached_to_id, url, uploaded_by, uploaded_at)
```

## State machine — warranty_claim

```
OPEN --decide(repair|replace|refund)--> DECIDED --fulfill--> FULFILLED --> CLOSED
OPEN --decide(deny)--------------------> DECIDED --------------------> CLOSED
OPEN --withdraw-------------------------------------------------------> CLOSED
```

Illegal, block these:
- `OPEN -> FULFILLED` (skips DECIDED — nothing to fulfill without a decision)
- `DECIDED(deny) -> FULFILLED` (a denial has nothing to fulfill)
- `FULFILLED -> DECIDED` (can't undecide after fulfilling; a bad replacement is a new linked claim, not a reopen)
- `CLOSED -> anything` (terminal; dispute = new claim with `prior_claim_id`, never reopen)
- claim creation where `now() > order_line_warranty.ends_at` (guard on creation, not a transition)

## State machine — return_request + refund

```
REQUESTED -> LABEL_ISSUED -> IN_TRANSIT -> RECEIVED -> GRADED
GRADED(match)    -> CLOSED_REFUNDED  (spawns refund: PENDING)
GRADED(mismatch) -> CLOSED_DENIED

refund: PENDING -> ISSUED -> SETTLED
                         \-> FAILED   (payment never completed)
              SETTLED -> REVERSED    (only via refund_reversal, evidence+notice required)
```

Illegal, block these:
- `REQUESTED -> RECEIVED` or `-> GRADED` (skips custody chain — this is exactly the empty-box gap; no scan, no receipt)
- any `-> REQUESTED` (no going backward)
- `CLOSED_* -> anything` (terminal; a later dispute is a new return_request referencing the old one)
- `PENDING -> SETTLED` (skips ISSUED)
- `ISSUED -> REVERSED` directly (this is the actual $309.5M bug — "issued without payment completing" got treated as reversible. Payment never completing is `ISSUED -> FAILED`, not a reversal. Only a *settled* refund can be reversed.)
- `FAILED -> SETTLED` (a failed attempt doesn't resurrect; retry creates a new `refund` row with `retry_of_refund_id`)
- `REVERSED` without a `refund_reversal` row where `notice_sent_at < charge_scheduled_at`

## Where the two features disagree — you pick

1. **Snapshot depth.** Warranty freezes terms at purchase; refund doesn't freeze a "return policy at purchase" (window days, restocking fee) — it reads current rules. If a seller shortens their return window after you bought, which applies? Warranty's own logic says freeze it. I'd freeze it too (`order_line_return_policy`, same shape as `order_line_warranty`) — flagging as a real gap in the pass-2 design, not something I've added silently above.
2. **Does a warranty-approved refund reuse the `refund` entity?** I put `refund.source_type: return|warranty_claim` above assuming yes — one settlement pipeline, not two. If you want warranty refunds handled entirely differently (e.g. always store credit, never cash), say so now, it's a schema fork.
3. **Quantity granularity.** Both features assume `order_line` = one unit. If `quantity > 1` is allowed per line, partial return + partial warranty claim on the same line gets messy fast. Cleanest MVP move: force `quantity = 1` per order_line (buying 3 creates 3 lines). Resolves both features' ambiguity at once.
4. Evidence shape — already resolved above (shared `evidence` table).

## Cut feature 2?

No — but shrink it. Keep the `issued/settled` split and the reversal-needs-evidence rule; that's pure schema and internal logic, no external dependency, and it's the single most validated finding across all three passes. Cut the *custody-event granularity* for v1: skip live carrier-webhook integration, collapse `label_created/dropped_off/carrier_scan` into one manual "seller marks received" action for now. Warranty needs zero external integration; full refund custody does need a real carrier feed to be worth anything, and you don't have one yet. Ship warranty first end-to-end; ship refund's state machine with the custody chain stubbed until carrier integration is actually in scope.

## Two decisions the data model left open, forced here

**1. Checkout must split a multi-seller cart into one `order` per seller.** The ADR's `order` has a single `status`/`tracking_number`/`shipped_at` — that only makes sense if one seller ships it. Nothing stops a buyer's cart from holding variants from two different sellers (single-seller-per-*product* doesn't mean single-seller-per-*cart*). Resolution: `POST /orders` accepts one cart, groups lines by seller, creates N `order` rows atomically (all-or-nothing across every seller, not just within one). Response is an array. This is what Amazon itself does — one checkout, multiple "orders" when sellers differ — and it means the ADR's `order` schema doesn't need to change.

**2. Magic-link consumption needs a `session` entity that isn't in the ADR.** Something has to hold "this opaque cookie value maps to this identity until this time." Adding: `session(id, identity_type: buyer|seller, identity_id, token_hash, expires_at, created_at)`. Small, uncontroversial, but new — flagging it rather than silently assuming it.

## Error model — one shape, everywhere

Spring Boot 3 ships `ProblemDetail` (RFC 7807) natively — use it instead of a hand-rolled shape, since it's already idiomatic for the pipeline and springdoc renders it as one reusable OpenAPI component referenced by every operation's error responses.

```
{
  "type": "https://api/errors/out-of-stock",   // stable machine code, URI form per RFC 7807
  "title": "Out of stock",
  "status": 409,
  "detail": "2 lines are no longer available in the requested quantity",
  "errors": [                                   // extension member, only on validation/conflict
    { "field": "lines[1].variantId", "reason": "requested 3, available 1" }
  ]
}
```

Every 4xx/5xx from every endpoint below returns this. `errors[]` is omitted when there's nothing itemized (e.g. 404, 401).

## Images — presigned upload + confirm

No standard REST shape for "get me a place to PUT a file, then tell the server it arrived" — here's the resolution, using the resource's own state rather than a verb in the path:

1. `POST /products/{productId}/images` or `POST /variants/{variantId}/images` — auth: owning seller. Body: `{ contentType, fileSizeBytes }`. Creates an `image` row with `status: pending`, returns:
   ```
   201 { id, status: "pending", uploadUrl, uploadFields, expiresAt }
   ```
   `uploadFields` = presigned POST conditions (content-length-range, content-type) — presigned POST, not PUT, because PUT can't enforce a size range.
2. Client uploads the file directly to S3 with those fields.
3. `PATCH /images/{imageId}` — auth: owning seller. Empty body. Server does an S3 HEAD; if the object exists, sets `status: stored`; if not, `409` with `type: upload-not-found`. Returns the current image resource either way.

An unused presigned URL just leaves an `image` row stuck at `pending` forever — cheap to ignore or garbage-collect later, and it never displays (only `stored` images render on the product page). No verb anywhere in the path; the transition is the resource's own status field.

## Checkout — the atomic call

`POST /orders` — auth: none (guest).

```
Request: {
  buyerEmail, buyerFullName,
  lines: [ { variantId, quantity, expectedUnitPrice? } ]   // expectedUnitPrice optional
}
```

Server-side, one transaction across the **whole cart regardless of seller**:
1. Find-or-create `buyer_identity` by email.
2. Group lines by the seller owning each variant's product.
3. For every line: lock/check `offer.stock_qty >= quantity` (conditional decrement, abort on failure) and compare current `offer.price` to `expectedUnitPrice` if the client sent one.
4. If **any** line fails either check, the entire call fails — no partial orders, no partial stock decrements, even across different sellers.
5. On success: one `order` row per seller group, `order_line` rows with everything snapshotted, stock decremented.

```
201 {
  buyerIdentityId,
  orders: [
    { id, sellerId, status: "placed", placedAt,
      lines: [ { id, productTitle, variantLabel, quantity, unitPrice } ] }
  ]
}
```

Failure cases, both `409 Conflict` using the shared error model:
- `type: out-of-stock` — `errors[]` lists `{ field: "lines[i].variantId", reason: "requested N, available M" }` for each short line.
- `type: price-changed` — `errors[]` lists `{ field: "lines[i].variantId", reason: "expected $X, now $Y" }`. Client re-fetches current prices and either re-submits accepting them (omit `expectedUnitPrice`) or drops the line.

Confirmation page renders straight from this response body — no follow-up `GET` or auth needed for the immediate post-checkout view. Returning to it later (refresh, different device) requires the magic link.

`GET /orders/{orderId}` — auth: buyer session, `404` (not `403`) if it exists but isn't theirs, to avoid confirming order-id existence to strangers. Full detail with lines.

Reaching it from the email link: the confirmation/history email contains a magic link (`role: buyer`). Clicking it → static page → `POST /sessions` → cookie set → frontend redirects to `/orders`. Same mechanism as any other buyer login, no separate "order lookup" concept needed.

## Checkout request shape

```
POST /orders

Request: {
  buyerEmail, buyerFullName, buyerPhone,
  shippingAddress: { line1, line2?, city, state?, postalCode, country },
  billingSameAsShipping: boolean,
  billingAddress?: { line1, line2?, city, state?, postalCode, country },
  lines: [ { variantId, quantity, expectedUnitPrice? } ]
}
```

## Billing: flag, not two mandatory forms

`billingSameAsShipping: boolean`, not two independent required addresses. `billingAddress` is required only when it's `false`; if `true`, any `billingAddress` sent anyway is silently ignored server-side (not a validation error — don't punish a frontend that always submits both fields for form-state simplicity). Standard pattern, smallest form for the common case.

## Validation

| Field | Required | Rule |
|---|---|---|
| `buyerPhone` | yes | E.164 (`^\+[1-9]\d{1,14}$`). No per-country format tables, no carrier lookup — just shape-check. Frontend collects country + local number and composes E.164; backend only ever sees/stores the composed form. |
| `shippingAddress.line1` | yes | non-empty |
| `shippingAddress.line2` | no | — |
| `shippingAddress.city` | yes | non-empty |
| `shippingAddress.state` | **no** | freeform string, unvalidated. Not every country has states/provinces, and conditionally requiring it per-country is a rabbit hole with no MVP payoff. |
| `shippingAddress.postalCode` | yes | non-empty only. Format varies too much cross-country to enforce a pattern without a country-specific rule table — deliberately not building one. |
| `shippingAddress.country` | yes | must match a maintained ISO 3166-1 alpha-2 allow-list (`US`, `CA`, `GB`, …), not freeform text. Rejects typos, gives the frontend a fixed dropdown. |
| `billingAddress.*` | same rules as shipping | only enforced when `billingSameAsShipping` is `false` |

All failures are one `422` with the existing error shape, `errors[]` itemized per field (`{ field: "shippingAddress.postalCode", reason: "required" }`).

## Snapshot, not a live address book

New entity, not on the ADR yet:

```
order_address(id, order_id, type: shipping|billing,
              full_name, phone, line1, line2, city, state, postal_code, country)
```

Always exactly **two** rows per order — shipping and billing — even when they're identical (`billingSameAsShipping: true` just copies shipping's values into the billing row at write time). This is deliberately simpler than conditionally omitting the billing row: every downstream reader (order detail, any future invoice view) can assume both rows always exist, no "fall back to shipping if billing is null" branching anywhere.

**Not stored on `buyer_identity`.** No reusable/editable saved address exists anywhere in this model — every checkout collects it fresh. That's not laziness for its own sake, it's the direct answer to your constraint: "a buyer editing an address later must not change what a past order says" is automatically true when there is no mutable copy to edit yet. The cost is buyers re-typing their address every order; that's a real, known tradeoff (pre-fill from last order is the obvious v2), not an oversight.

## Touches the checkout split decision from last turn

Since one checkout can produce N `order` rows (one per seller), each of those N orders gets its **own** pair of `order_address` rows — the same address data duplicated across every sibling order from that one checkout, not shared by reference. Consistent with the same reasoning: an `order` must be a fully self-contained record, never dependent on a join back to some other order or a "checkout session" concept that doesn't otherwise exist in this schema.

- `order_address` — new table, as above.
- `order` implicitly still has no `phone` column of its own — phone lives only inside `order_address` rows (both shipping and billing carry a `phone`, since a buyer might want calls routed to a different number for billing vs. delivery; if you want one phone number for the whole order instead of per-address, say so — that's a smaller table, one column moves from `order_address` to `order`).
